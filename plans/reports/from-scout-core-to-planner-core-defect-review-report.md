# omnipet-core defect + upgrade review (scout-core -> planner-core)

Read-only pass over `omnipet-core/src/main/java/io/github/salyvn/omnipet/core/**` (15,265 lines, 2026-09-03). No files modified, no gradle run. Paths below relative to `omnipet-core/src/main/java/io/github/salyvn/omnipet/core/`.

## Summary

- Persistence/saga design solid overall (atomic `.bak` writes, escrow saga transitions complete, splitmix64 RNG correct, revision CAS everywhere); most findings are bounds, lock hygiene, scan cost, not logic bugs.
- 1x P1: shared static SnakeYAML `Yaml` instances used from concurrent async tasks (SnakeYAML `Yaml` documented not thread-safe); failure mode is quarantine of a healthy player file.
- 8x P2: player-lock registry spins forever on same-thread re-acquire; unbounded player/definition file reads; stray filename bricks all pet-definition reads; unbounded lock map in purchase journal; O(N)+hard-throw escrow scan per join; incubation cancel/complete blocked at 128 tokens; stamina regen always writes + invalidates release preview; at-least-once internal reward delivery.
- ~14x P3 (corrupt-outbox exceptions escaping, positional skill binding IDs, cooldown overflow, quadratic definition scans, order-dependent hatch determinism, dead `EffectBudget`, per-tick allocations).
- 15 files >200 lines; `PetDefinitionStudioService` (607) is the clear split candidate.

## Upgrade opportunities

- One `BoundedFiles.readString(path, maxBytes)` helper used by all 6 file repos; today each journal re-implements the 16 KiB check and two repos have none.
- Lock registry: owner-thread tracking + bounded wait + explicit re-entrant-acquire error; unify `FilePurchaseJournal` locks and `CultivationItemActionFileJournal` `synchronized` onto `EggEscrowLockRegistry` (refcounted, evicting).
- `ThreadLocal<Yaml>` in `YamlDocuments`; add parallel-load test.
- Directory-scan hygiene: skip-and-report stray filenames instead of throwing (`YamlPetDefinitionFiles`, `CultivationItemActionFileJournal`, `PurchaseJournalScanner`); single-scan `readAll()` for pet definitions.
- Journal lifecycle: archive terminal escrow/purchase/action records to a sub-directory on transition so per-join scans stay small and the 10k bound is never hit.
- Hatch determinism: sort candidates/bands by ID; bump `ALGORITHM_ID` to `splitmix64-v2` if outputs change.
- Stamina: no-op regen at cap; exclude stamina fields from `ReleaseIdentity.petFingerprint`.
- Skill bindings: stable default `bindingId`; cap durations in `SkillBinding`.
- Remove `EffectBudget` (+2 tests) or wire it.
- `ReleaseOutboxStore.isUsable` decodes fully; catch corrupt entries into result statuses.

1. Does `PaperReleaseInternalRewardPort` dedupe by `transactionId`? If not, the at-least-once P2 is a real double-reward bug.
2. Is `RepositoryProgressionService.regenerateStamina` meant to be called on a timer from Paper later? If yes the always-write P2 becomes per-pet disk churn.
3. Do any Paper wrappers call `snapshot`/`withLocked` on the same player from inside a core `withLocked` lambda? Core paths checked; Paper lambdas out of scope.
4. Is `PurchaseTransactionCoordinator.shared()` surviving a plugin reload (new classloader) a supported scenario? Determines whether the lock-registry spin is reachable in practice.
